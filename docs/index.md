# django-encryption-suite

django-encryption-suite encrypts Django model fields and uploaded files per silo, with
pluggable KMS backends. It also offers system-wide encryption, `key_set="system"`, for the columns
no group of users scopes, and an optional blind index that keeps an encrypted column searchable.

## Features

Mark model fields as encrypted, and store uploads with `EncryptedFileField`.
Field values and file contents are encrypted before they reach the database or
the storage backend, and decrypted when read back. Encryption is scoped to a
**silo**, and each silo's data is encrypted under its own keys. A **key set** binds a
silo adapter to a key store: by default a field uses the `default` key set, the
groups of users your project defines, typically a tenant or team. The `system` key
set is a single silo for system-wide data, and a project can declare more, such as
one silo per user. A field names its key set with `key_set`.

```python
class Patient(models.Model):
    name = models.CharField(max_length=100)             # plaintext — queryable
    date_of_birth = EncryptedDateField()                # encrypted at rest
    national_id = EncryptedIntegerField(null=True)      # encrypted at rest
    notes = EncryptedTextField(null=True, blank=True)   # encrypted at rest
    scan = EncryptedFileField(                          # file contents encrypted in storage
        display_name_field="scan_name", null=True, blank=True
    )
    scan_name = EncryptedCharField(max_length=255, null=True, blank=True)  # its filename, encrypted
```

> **Binding data within a silo:** each silo has its own DEK, so a row moved to
> another silo already fails to decrypt. To tie encrypted data to something
> *inside* a silo — the user who owns it, or the parent record it belongs to —
> pass those columns to each encrypted field's `aad=`, e.g.
> `aad=("owner",)`. If one of them is changed, for example to hand a record to
> another user on the same team, its encrypted fields fail to decrypt instead
> of reading as the new owner's. See
> [Row-identity binding](security.md#row-identity-binding-optional).

Not every column is scoped to a group of users. A user's email address or
username belongs to the user, and the columns a sign-in reads must not depend on
a team's KMS. Those declare `key_set="system"` — same field
types, same lenient reads, no team in the context — and use the silo of the
`system` key set, whose keys the env key store wraps under `ENV_KEY_STORES` from
your settings:

```python
class CustomUser(AbstractUser):
    email = EncryptedEmailField(key_set="system", blank=True, blind_index=True, normalize="casefold")
    username = EncryptedCharField(
        key_set="system", max_length=150, unique=True, blind_index=True, normalize="casefold"
    )
```

Around the encryption itself, the package provides:

- **A blind index**, `blind_index=True` on any encrypted field, for the columns you
  still have to look a value up in. It stores a keyed digest where the database
  can index it, which answers `exact`, `iexact` and `in` and holds the
  plaintext unique. Every other lookup is refused rather than matched against
  nothing, sorting and ranges are not available, and the index discloses
  equality — so declare it only where a lookup needs it.
- **Key lifecycle.** Key encryption keys created by hand or provisioned
  automatically, rotation of both key layers with re-encryption, scheduled
  deletion of a silo's keys, and an append-only record of every key event.
- **Silo adapters** for SaaS Pegasus teams, django-tenants, any model you
  name, or a composite of these, plus an optional
  [ready-made team app](simple-teams.md) for projects
  with no team model of their own.
- **KMS adapters** for GCP, AWS, Azure Key Vault, HashiCorp Vault, IBM Key
  Protect / HPCS, OCI Vault, Infisical, Fly.io, and a local mode for
  development, with OIDC federation for keyless access across clouds.
- **Admin screens** to find drift between the database and the KMS, act on
  keys, review key events, and test a round-trip in isolation.
- **Safe error messages.** Every failure is a typed error carrying a generic,
  translated message for users, and a stable error code and one clean log line
  for operators.

## Design

The package uses **envelope encryption**:

1. Each silo (tenant/team) has a **data encryption key (DEK)** per purpose —
   one for fields, one for files, and a third for the blind index where a field
   declares one — generated by the configured
   [crypto backend](crypto-backends.md) — AES-256-GCM by default. Files are
   encrypted in streamed segments, so a large file is processed in chunks.
2. Each DEK is encrypted by a **key encryption key (KEK)** held in an external
   KMS (GCP, AWS, Azure, HashiCorp Vault, IBM, OCI, Infisical, Fly.io, or
   local dev).
3. The encrypted DEKs are stored in the database. A plaintext DEK never
   touches disk.
4. On each field read or write and each file upload or download, the engine
   decrypts the DEK via KMS and uses it to encrypt or decrypt the data.
5. Decrypted DEKs are cached in-process with a configurable TTL to avoid a
   KMS call on every access.

A [`key_set="system"` column](system-wide-silos.md) follows the same steps
under the system silo's keys, with one change: the env key store wraps them
under `ENV_KEY_STORES` from your settings, so nothing is called off the machine. That
is what lets a sign-in read those columns while the KMS is still being set up.
