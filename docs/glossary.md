# Glossary

This glossary defines the terms the django-encryption-suite documentation uses. It groups
them by topic and lists them alphabetically within each group. New to envelope
encryption? Read [Core concepts](concepts.md) first for how these pieces fit
together.

---

## Encryption concepts

| Term | Stands for | Definition |
|---|---|---|
| **AAD** | Additional Authenticated Data | Extra context bytes passed to AEAD encryption that are authenticated but not encrypted. This package binds AAD at two layers: (1) at the field layer, optionally, when an encrypted field declares `aad=`, the listed columns' values on the row are bound into that field's value, so tampering with a listed column makes the field fail to decrypt; and (2) at the wrap layer, the `silo_uid` is bound into every wrapped DEK (via `AbstractKmsAdapter._wrap_aad` for byte-AAD adapters, or AWS `EncryptionContext` for AWS KMS), so a wrapped DEK cannot be opened on behalf of a different silo. The two layers serve different purposes and should not be conflated. |
| **AEAD** | Authenticated Encryption with Associated Data | An encryption scheme that provides both confidentiality (data is unreadable without the key) and integrity (any tampering with the ciphertext or its associated context is detected on decryption). AES-256-GCM is an AEAD scheme. |
| **AES** | Advanced Encryption Standard | A symmetric block cipher adopted as a standard by NIST. django-encryption-suite uses AES as the underlying algorithm for field encryption, in 256-bit (`AES256_GCM`, `AES256_EAX`, `AES256_GCM_SIV`) or 128-bit (`AES128_GCM`) variants depending on the configured key template. |
| **ChaCha20** | — | A stream cipher. Paired with Poly1305 it forms the ChaCha20-Poly1305 AEAD (`CHACHA20_POLY1305`), an alternative to AES-256-GCM supported by the pyca-cryptography backend — often preferred on hardware without AES acceleration. |
| **EAX** | Encrypt-then-Authenticate-then-Translate | An alternative authenticated encryption mode for AES supported by this package via the `AES256_EAX` key template (Tink backend). |
| **GCM** | Galois/Counter Mode | A mode of operation for AES that provides both encryption and authentication in a single pass. AES-256-GCM (256-bit key, GCM mode) is the default algorithm in this package. |
| **HKDF** | HMAC-based Key Derivation Function | A key-derivation function. Tink's streaming AEAD templates (`AES256_GCM_HKDF_4KB`, `AES256_GCM_HKDF_1MB`, `AES128_GCM_HKDF_4KB`) and the pyca-cryptography backend's streaming format both derive a fresh per-file key with HKDF-SHA256 from the data key and a random salt, then encrypt the file segment by segment under it. |
| **Poly1305** | — | A message authentication code. Combined with the ChaCha20 stream cipher to form the ChaCha20-Poly1305 AEAD scheme (`CHACHA20_POLY1305`) supported by the pyca-cryptography backend. |
| **SIV** | Synthetic Initialization Vector | A nonce-misuse-resistant AEAD construction. AES-256-GCM-SIV (`AES256_GCM_SIV`, pyca-cryptography backend) stays secure even if a nonce is accidentally reused — a real safety margin over plain GCM. |

## Envelope encryption

| Term | Stands for | Definition |
|---|---|---|
| **Cryptography** | - | [PyCA Cryptography](https://github.com/pyca/cryptography) is an open-source cryptographic library maintained by the Python Cryptographic Authority (PyCA). It includes both high level recipes and low level interfaces to common cryptographic algorithms such as symmetric ciphers, message digests, and key derivation functions.
| **DEK** | Data Encryption Key | The key that directly encrypts and decrypts your field values. Each silo has its own DEK. In this package, the DEK is generated by the configured [crypto backend](crypto-backends.md) (AES-256-GCM by default) and stored wrapped on a `DataEncryptionKey` row. |
| **KEK** | Key Encryption Key | The key that encrypts the DEK. Held in your external KMS provider. The KEK never leaves the KMS — encrypt and decrypt operations on the DEK happen server-side within the KMS. Each KEK the deployment knows about has a local `KeyEncryptionKey` row recording its state. |
| **Key decryption** | — | Decrypting an encrypted keyset back to the plaintext DEK using the KEK. This happens in the KMS, and the plaintext DEK is returned to the application over a secure channel. Some literature calls this "key unwrapping". |
| **Key encryption** | — | Encrypting a DEK with a KEK. The result is an "encrypted keyset" — ciphertext that can only be decrypted by the KMS that holds the KEK. Some literature calls this "key wrapping". |
| **Keyset** | — | The serialized DEK stored (wrapped) on a `DataEncryptionKey` row. Its format depends on the crypto backend: the Tink backend stores a Tink keyset (a protobuf holding one key plus metadata about which key is primary); the pyca-cryptography backend stores a compact `version \| aead_id \| key` blob. |
| **Tink** | — | [Google Tink](https://developers.google.com/tink) is an open-source cryptographic library. It is one of the two crypto backends (the `[tink]` extra), where it generates keysets, performs AEAD and Streaming AEAD encryption/decryption, and serializes keyset material. It also underlies the `GcpTinkKmsAdapter` and `AwsTinkKmsAdapter` KMS adapters. |

## Key management and cloud services

| Term | Stands for | Definition |
|---|---|---|
| **ADC** | Application Default Credentials | Google's credential-discovery mechanism: client libraries automatically locate credentials from the environment (host metadata server on GCP, a key file, or local `gcloud` login). `GcpTinkKmsAdapter` always authenticates this way; on GCP it is keyless via the host metadata server. |
| **AWS** | Amazon Web Services | Amazon's cloud computing platform. Its KMS offering is AWS KMS. |
| **GCP** | Google Cloud Platform | Google's cloud computing platform. Its KMS offering is Cloud KMS. |
| **HCP** | HashiCorp Cloud Platform | HashiCorp's managed cloud offering. HCP Vault is a hosted version of HashiCorp Vault. |
| **HPCS** | Hyper Protect Crypto Services | An IBM Cloud offering that provides a dedicated, FIPS 140-2 Level 4 certified HSM for key management. Supported by the IBM KMS adapter. |
| **IAM** | Identity and Access Management | A cloud provider service that controls who can access which resources. Used to restrict which applications and roles can use KMS keys. |
| **KMS** | Key Management Service | An external service that manages cryptographic keys and performs encryption/decryption of DEKs on behalf of callers. Examples: AWS KMS, GCP Cloud KMS, Azure Key Vault, HashiCorp Vault. |
| **OCID** | Oracle Cloud Identifier | Oracle Cloud Infrastructure's globally unique resource identifier format, used to identify KMS keys in the OCI Vault adapter. |
| **OIDC** | OpenID Connect | An identity layer built on OAuth 2.0 that provides signed identity tokens (JWTs). A platform such as Fly.io issues its workloads OIDC tokens, which the `oidc` credential strategy exchanges with a KMS provider for keyless authentication. |
| **SigV4** | Signature Version 4 | AWS's request signing protocol. Used by the Vault IAM AWS credential strategy to create a signed `GetCallerIdentity` request that Vault can verify. |
| **STS** | Security Token Service | A token-exchange service that trades a caller's identity token for temporary, short-lived credentials. AWS STS backs the AWS `oidc` strategy and the Vault IAM AWS strategy; GCP's STS (`sts.googleapis.com`) performs the first leg of Workload Identity Federation, exchanging an OIDC token for a federated token before service-account impersonation. |
| **TLS** | Transport Layer Security | The cryptographic protocol that secures HTTPS connections. The package's calls to cloud and network KMS APIs use TLS. The Fly.io adapter talks to a Unix socket inside the machine, and the env key store makes no network call. |
| **WIF** | Workload Identity Federation | GCP's mechanism for keyless authentication: an external OIDC token is exchanged (via STS) for short-lived GCP credentials by impersonating a service account, so no service-account key file is needed. Used by `GcpKmsAdapter` with `CREDENTIAL_STRATEGY: "oidc"`. |

## django-encryption-suite concepts

| Term | Stands for | Definition |
|---|---|---|
| **Crypto-shred** | — | Destroying data by destroying the key that decrypts it, rather than by overwriting the data itself. Clearing a `DataEncryptionKey` row's `encrypted_keyset` shreds that silo's field and file data in the live database. A database backup taken before the shred still holds the wrapped key, and stays readable for as long as the key encryption key that wraps it exists. Destroying that key encryption key is what makes the shred irreversible everywhere, backups included. |
| **Blind index** | — | A keyed hash of a value, stored in a column or a table of its own so the encrypted column can still be matched by exact value. Makes `exact`, `iexact` and `in` work on any encrypted column declaring `blind_index=True`; every other lookup is refused, because a keyed hash answers equality and nothing else. Reveals equality — two rows holding the same value index alike — so declare it only where a lookup needs it. Keyed, because an unkeyed hash of an email address is recovered by hashing a word list: from the system silo's index key for a [`key_set="system"` column](system-wide-silos.md), and from the silo's own index key for a [silo column](encrypted-data.md#finding-a-row-by-its-value), which is what makes two silos index one value differently. |
| **Blind index storage** | — | Where a field keeps its digests: `blind_index_storage="column"`, a companion column on the model's own table, the default and the cheapest; or `"table"`, a row in the package's `BlindIndexEntry`, which adds no schema to the model's app and so is the only option for a model the project does not own. |
| **Silo** | — | Any group of data that shares key isolation: typically a tenant, team, or organization in your application, or the one system silo for system-wide data. A silo adapter resolves it. Each silo's data is encrypted under its own key, so compromising one silo's key does not expose another's data. |
| **Key set** | — | One silo adapter and one key store, named in `KEY_SETS`. A field names its key set with `key_set` (`default` when absent). Fields that name the same key set share its data keys in each silo, and a key set gets its own data keys, which `KEY_SETS` may put on a different store from another key set's. Key sets bound to one adapter share its silos. Two names are reserved: `default`, and `system` (built in, bound to the system adapter). |
| **Silo reference** | — | A key set plus the silo adapter's raw uid. It identifies one silo's keys in that key set anywhere in the code; the same uid in two key sets bound to different adapters names two silos. |
| **Key store** | — | Where key encryption keys live. Two types: an env store (key material your settings supply to the process) and a KMS store (a remote service that wraps keys). `KEY_SETS` chooses a store for each key set; a field never names one. |
| **Named store** | — | One entry in a key store registry (`KMS_KEY_STORES` or `ENV_KEY_STORES`), such as `aws` or `login`. Names are unique across both registries. `KEY_SETS` chooses one per key set. |
| **Sharing** | — | One KEK shared across silos (`SharedKekStrategy`), or one KEK per silo (`PerSiloKekStrategy`). |
| **Tombstone** | — | A key row that outlives its key material. At deletion a `DataEncryptionKey`'s `encrypted_keyset` is cleared and its status becomes `deleted`, but the row stays, keeping `silo_uid`, `purpose`, and its reference to the key encryption key. The record of the key survives for audit; the key does not. A `KeyEncryptionKey` row works the same way — it is never deleted, and a terminal `deleted` status is its last-known record. Tombstones are what let the package distinguish "this silo's key was destroyed" from "this silo never had one". |
| **System-wide silo** | — | The one silo of the `system` key set, which `key_set="system"` columns are encrypted under: system-wide columns that no group of users scopes, such as a user's email address or username. It has a silo's three data keys on rows with the silo uid `system`, wrapped by the env key store under `ENV_KEY_STORES`, and needs no silo in the context — which is why sign-in does not depend on a team's KMS. See [System-wide silos](system-wide-silos.md). |
| **Env key store** | — | A named store built into the package that wraps keys under `ENV_KEY_STORES`, key material held in the project's settings, and shares one key encryption key across every silo that uses it. See [Configuration](configuration.md#env_key_stores). |
| **KMS name** | — | The name a `KMS_KEY_STORES` block goes by, or `system`. Every key encryption key row records it, and every unwrap goes through the block of that name, so a name never changes once rows use it. |
| **TTL** | Time To Live | How long a decrypted DEK is cached in process memory before the engine goes back to KMS to re-decrypt it. Controlled by the `DEK_CACHE_TTL` setting. |
| **UID** | Unique Identifier | A string that uniquely identifies a silo across all types, produced by the silo adapter (e.g., `"team-42"`, `"tenant-acme"`). |

## Web application and infrastructure

| Term | Stands for | Definition |
|---|---|---|
| **API** | Application Programming Interface | A defined interface for communication between software components. In this documentation, typically refers to REST APIs exposed by KMS providers. |
| **ASGI** | Asynchronous Server Gateway Interface | The standard Python interface for asynchronous web servers (e.g., uvicorn, Daphne). Multiple requests may share a single thread via async tasks. |
| **RAM** | Random Access Memory | A computer's working memory. Decrypted DEKs exist only in RAM, never on disk. |
| **SQL** | Structured Query Language | The standard language for querying relational databases. SQL injection is one of the threats that encryption at rest helps mitigate. |
| **WSGI** | Web Server Gateway Interface | The standard Python interface for synchronous web servers (e.g., gunicorn with sync workers). Each request runs in its own thread. |

## Security and compliance

| Term | Stands for | Definition |
|---|---|---|
| **DBA** | Database Administrator | A person with direct access to the database. Encryption at rest protects against a compromised or malicious DBA reading sensitive field values. |
| **GDPR** | General Data Protection Regulation | A European Union regulation on data protection and privacy. Encryption at rest is one technical measure that can support GDPR compliance. |
| **HIPAA** | Health Insurance Portability and Accountability Act | A US federal law that requires safeguards for protected health information. Encryption at rest and audit logging can help satisfy HIPAA requirements. |
| **IDOR** | Insecure Direct Object Reference | A vulnerability where an attacker manipulates an identifier (e.g., a team ID in a URL) to access another user's data. Per-silo encryption means that even if an IDOR exposes a row, the encrypted fields cannot be decrypted without the correct silo context. |
| **PCI DSS** | Payment Card Industry Data Security Standard | A security standard for organizations that handle credit card data. Requires encryption of cardholder data at rest and regular key rotation. |
| **SIEM** | Security Information and Event Management | A system that aggregates and analyzes security logs. Audit log entries from django-encryption-suite can be routed to a SIEM for monitoring and alerting. |
| **SOC 2** | System and Organization Controls 2 | An auditing framework for service organizations that evaluates controls around security, availability, and confidentiality. Key rotation and audit logging support SOC 2 compliance. |
